## Findings

### F1 — Failed readiness is logged at Error by the framework; the approved contract and T023 say Warning, and no code logs it — CONFIRM

`contracts/http-baseline.md` (Audit): "Failed readiness checks are logged at Warning, without the connection string." T023: "logs failures at Warning without the connection string". The implementation contains no logging code; the only log line comes from the framework's `DefaultHealthCheckService`, observed in every run as `fail: Microsoft.Extensions.Diagnostics.HealthChecks.DefaultHealthCheckService[103] Health check database with status Unhealthy completed after ...ms with message '(null)'`. `fail:` is Error level, not Warning. So the approved wording ("Warning") is not met; the clause "without the connection string" is met (0 hits for the planted passwords/connection strings in the log; the only exception logged is the timeout `TaskCanceledException`, which carries no connection data). Practical effect: probe traffic against an unreachable database writes an Error line per probe, which can trip error-rate alerting that expects Warning. The commit message and tasks tick do not disclose the discrepancy.
*Action: owner decides: either amend the contract Audit line and T023 to "logged at Error by the framework's health check service, without the connection string" (with the owner's amendment record), or have a follow-up task set the `Microsoft.Extensions.Diagnostics.HealthChecks.DefaultHealthCheckService` category to Warning-or-lower and log an explicit Warning. Implementing agent must not self-amend.*

### F2 — Stubbed readiness tests do not prove the `ready` tag selection — MINOR

`ReadinessFactory` clears all registrations and adds exactly one, tagged `ready`. With one tagged registration, `Predicate = r => r.Tags.Contains("ready")` and "run all checks" behave identically, so T018 would still pass if `/health/ready` ran every check. They would fail if it ran none (empty report is Healthy, so the Unhealthy case would return 200), which is a real guard. The liveness side is meaningful: `LivenessStaysHealthyWhileTheReadyCheckIsUnhealthy` would fail if `/health` ran all checks (`Predicate = _ => false` is the only thing keeping it green); it passed before the implementation as a regression guard, which the task wording (T020, spec US1 scenario 2) accepts. T019 cannot pass for the wrong reason: an unmapped route would give 404, not 503, and a startup crash would throw from `CreateClient()`; the empty string is also verified to open no connection.
*Action: follow-up (next feature touching health): add a second registration without the `ready` tag that is Unhealthy and assert `/health/ready` is still 200 (and one tagged Healthy plus one untagged Unhealthy). No change needed for merge.*

### F3 — No test asserts the 5 s timeout is applied — MINOR

The `Configure<HealthCheckServiceOptions>` that sets `Timeout` is the mechanism behind FR-004 and the SC-002 "within 5 seconds" claim, yet every test replaces the registrations (stub) or uses an empty connection string that fails instantly. If the `Configure` were dropped or reordered before `AddDbContextCheck`, all 16 tests would still pass and the registration would silently fall back to the 30 s default. I verified the behaviour by hand (5.0 s against a 15 s connect timeout) but nothing in the suite guards it. A cheap test would resolve `IOptions<HealthCheckServiceOptions>` from the real factory and assert the `database` registration's `Timeout == 5 s`.
*Action: implementing agent adds one options-level assertion in a follow-up (or accepts the by-hand evidence in notes.md); not a merge blocker.*

### F4 — SC-002 says "LocalDB stopped"; the quickstart (correctly) uses OFFLINE — CONFIRM

spec.md SC-002 and the tasks.md Phase 4 Independent Test say "with LocalDB stopped, it returns 503 within 5 seconds". The quickstart replaces this with `ALTER DATABASE BookingApi SET OFFLINE`, explaining that LocalDB restarts itself on the next connection. This is the right call (my run against LocalDB confirmed auto-start: the first request took 2.2 s, a LocalDB cold start, and then answered), but it is a deviation from the literal approved text that the owner will be certifying by hand. Note also that OFFLINE exercises the fast-fail path (login refused immediately), not the 5 s hang; the 5 s bound itself is only evidenced by my unroutable-host run and by the spec edge case "hangs on an unresponsive server", which has no automated test (F3).
*Action: owner acknowledges that SC-002 is verified via OFFLINE rather than a stopped instance (and optionally amends SC-002 wording at merge review); no code change.*

### F5 — First request against an unroutable host exceeds 5 s by about 0.4 s wall-clock — MINOR

The check itself is cut at 5.02-5.03 s (log `completed after 5027ms`), but the first request after startup took 5431 ms server-side / 5.49 s at curl (cold-path overhead), and 5.02 s on the second call. FR-004 says "the readiness check MUST complete within 5 seconds"; the check's own budget holds, the HTTP round trip is marginally above on a cold start. A probe with a 5 s client timeout could abandon that first call.
*Action: none for merge; owner may note it when running SC-002 (the quickstart's "under 5 seconds" is strict only for warm calls). A 4 s timeout would leave headroom if the owner cares.*

### F6 — Failure cause is not diagnosable from the log — MINOR

Missing, empty, malformed, offline and nonexistent-database cases all log the same line with `message '(null)'` and no exception, because `CanConnectAsync` returns false instead of throwing; only the timeout case includes an exception. This is safe (no leakage, which is why it is MINOR) but an operator cannot tell "no connection string" from "server down" from "bad credentials" from the log. Related to F1: a deliberate Warning log could include a fixed reason category ("not configured" vs "unreachable") without exposing the connection string.
*Action: none for merge; consider alongside the F1 decision.*

### F7 — Quickstart nits: unconditional DROP in clean-up, and the secret differs from T025's string — MINOR

(a) Step 1 guards creation ("if `BookingApi` is not listed, create it"), but "Clean up (optional)" runs `DROP DATABASE BookingApi` with no matching guard; a user who skipped creation because a `BookingApi` database already existed (possibly someone else's, which the rulebook's dedicated-database rule is meant to catch) would drop it. Nothing runs unless the user runs it, so this is not an unsafe default. (b) The quickstart connection string adds `TrustServerCertificate=True` to the T025 string; this is needed with current SqlClient encryption defaults on LocalDB and is only a local development value in user-secrets, but it is an undocumented delta from T025. Other commands check out: `sqlcmd -E -Q` syntax is valid, `database_id > 4` lists user databases, `ALTER DATABASE ... SET OFFLINE WITH ROLLBACK IMMEDIATE` / `SET ONLINE` touch only `BookingApi`, `dotnet user-secrets set ... --project src/BookingApi.Api` matches the new `UserSecretsId`, `curl.exe` (not the PowerShell alias) is used, and `--launch-profile http` listens on `http://localhost:5132`, matching `launchSettings.json`.
*Action: implementing agent may add "only if you created it in step 1" to the clean-up and one sentence on `TrustServerCertificate`; not a merge blocker.*

### F8 — Housekeeping: Api.csproj gained a UTF-8 BOM; EF reaches Api only transitively — MINOR

`dotnet user-secrets init` rewrote `BookingApi.Api.csproj` with a BOM (diff line 1). The other csprojs and `launchSettings.json` already carry a BOM, so the tree is now consistent and the change is harmless. `Api -> Infrastructure` brings EF packages onto Api's compile classpath transitively, which is inherent to the approved ADR-001 reference (the dependency tests assert project references, not packages, for Api/Infrastructure); no EF type is used in Api (grep: none).
*Action: none.*
